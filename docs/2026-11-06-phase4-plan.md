# Phase 4 plan: Query diagnostics, then the process panel

Goal: the Ecto tab says *why* a page is slow, not only what ran. Repeated queries
(N+1) are flagged where they happen, and any captured SELECT can be explained in one
click. The process panel follows as its own batch (4b).

Decisions go into a new ADR 08 (query diagnostics), ADR 02 (callback spans), ADR 03
(the bounded explain payload) and ADR 05 (Ecto plugin options). Socket RTT and
`handle_info` tracing are deferred.

## Where we start

- Ecto events carry `repo`, truncated `sql`, redacted and inspected `params`, `source`,
  `result`, `times`, a truncated `stacktrace` (only with the repo's `stacktrace: true`)
  and `caller?` (`plugins/ecto.ex`). The raw params and the full SQL are gone after
  `collect/3`.
- An event knows its session (request or LiveView sid), not the LiveView callback it ran
  in: "one callback" cannot be told apart today.
- `Ecto.Adapters.SQL.explain/4` takes a **queryable**, not SQL text (verified in
  `deps/ecto_sql/lib/ecto/adapters/sql.ex`): we cannot use it on captured queries.
- `ecto_sqlite3` is `only: :dev`; tests use `DemoWeb.FakeRepo` (no database). The
  harness has an N+1 page (`/posts`) with a preloaded variant.

## Design

**Callback spans.** The Collector already sees LiveView callback telemetry in tracked
processes. On each callback `:start` and `:stop` it bumps a per process span id
(`Process.put`, tracked processes only, after attribution). `Context.span` hands it to
`collect/3`, and the collector stamps it on the event (`Event.span`, like
`Event.plugin`). A span is one callback, or the gap between two callbacks (where
`handle_info/2` runs: it has no telemetry). In a request, the whole request is one span.

**N+1 detector** (pure, panel side, `PhoenixDevToolbar.NPlusOne`). Key: `{sid, span,
sql, origin}`, where origin is the first stacktrace frame, or nil without
`stacktrace: true`. A group reaching the threshold is an N+1. Memory: counts are kept
for the current span of each sid only; detected groups are capped (50 per page).
Threshold: the Ecto plugin option `n_plus_one: 5` (an integer >= 2, or `false` to
disable), validated in `init/1`. UI:
- the Ecto badge gains "N+1 ×k" at `:warn`;
- the Ecto tab lists detected groups above the queries (SQL, origin, count, where);
- rows from the threshold on get an `N+1` tag;
- without origins, a hint says `stacktrace: true` makes the detector precise.

**EXPLAIN.**
- **Capture** (in `collect/3`): only for a SELECT (leading `SELECT`/`WITH` after
  whitespace and comments, checked on the raw SQL), the event keeps `explain: %{sql,
  params}`:
  - the full SQL up to 16 KB;
  - the raw `params` sent to the adapter (not `cast_params`), only when there are 50 or
    fewer and each is a scalar (integer, float, boolean, nil, a binary up to 1 KB, or a
    `Date`/`Time`/`NaiveDateTime`/`DateTime`/`Decimal`). The walk is bounded by those
    limits.

  Anything else stores `explain: nil` ("cannot explain: params too large"). The payload
  is never rendered: params stay redacted on screen, and the raw ones only go back to
  the database.
- **Run** (`PhoenixDevToolbar.Explain`, in the Ecto tab's `start_async`):
  - The client sends only a seq. The component reads that event from the Store, scoped
    to the page's sids.
  - The repo must be one of the plugin's configured repos.
  - The SQL is re-checked as a SELECT, and multiple statements are refused.
  - Prefix by adapter: Postgres `EXPLAIN`, MyXQL `EXPLAIN`, SQLite3 `EXPLAIN QUERY PLAN`.
    Other adapters show no button. **Never `ANALYZE`**: it runs the query.
  - It runs through `repo.query/3` (public API) inside `repo.transaction/2` with a
    forced rollback and a 5 s timeout.
  - The result is formatted with `Ecto.Adapters.SQL.format_table/1` and truncated, and
    shown under the row.
  - Errors (timeout, a database error) show in the row and never break the tab.

## Tasks

Each task is one subagent slice (under ~40 turns), tests first, committed on its own.
Every task gets one combined reviewer before the next starts. At the end, two
independent reviewers (technical and product) run the `feature-review` checklist on the
whole range.

1. **(R) Callback spans.** Collector bumps the span on LiveView callback `:start` and
   `:stop` (mount, handle_params, handle_event, render; component callbacks too) after
   attribution; `Context.span`, `Event.span`, stamped like `plugin`. Untracked fast path
   unchanged (one `Process.get`). Files: `collector.ex`, `context.ex`, `event.ex`.
   Tests: two `handle_event`s on a real host LiveView give two spans; queries in one
   callback share one; request events share the request span.
2. **N+1 detector.** `NPlusOne` fold (pure), the Ecto plugin's `n_plus_one:` option, Ecto
   summary and badge, detected groups and row tags in the Ecto tab. Files: new
   `n_plus_one.ex`, `plugins/ecto.ex`, `panels/ecto.ex`, `components.ex`, `panel.css`.
   Tests: unit tests for the fold (threshold, per span, without origin, caps), the option
   matrix, and end to end on a host LiveView that runs an N+1 in one `handle_event` and
   the same query once per click in five clicks (no N+1).
3. **(R) EXPLAIN capture.** SELECT check, bounded payload in `collect/3`. Files:
   `plugins/ecto.ex`, `truncate.ex` if a helper fits there. Tests: SELECT/WITH/comments,
   writes skipped, params limits (count, size, types), payload never in the rendered row.
   Hot path cost measured with a quick benchmark in the scratchpad, numbers in the commit.
4. **(R) EXPLAIN run.** `Explain` module and the Ecto tab button, async result, errors.
   `ecto_sqlite3` becomes `only: [:dev, :test]` with a test SQLite repo (tmp file,
   created in `test_helper.exs`). Files: new `explain.ex`, `panels/ecto.ex`,
   `components.ex`, `panel.css`, `mix.exs`, `test/support`. Tests: explain a captured
   SELECT through the panel; a seq from another page is refused; an unconfigured repo is
   refused; a write is refused; the rollback holds; a database error shows in the row.
   Verify `format_table/1` and `query/4` in the ecto_sql 3.12 tarball (our minimum).
5. **Docs and harness.** ADR 08 (new, index row), ADR 02, 03 and 05 updates, README
   (Ecto options), CHANGELOG, roadmap ticks. Harness: `/posts` shows the badge; add an
   explain demo. `mix precommit`, the LiveView 1.1 run, the prod fixture, and a browser
   check (light and dark). Then the double final review.

## Risks

- **Hot path cost**: spans add one `Process.put` per callback start and stop, in tracked
  processes only. The explain payload adds a SELECT prefix check and a params walk
  bounded by 50 scalars. Measured in task 3; the untracked path is unchanged.
- **Production footprint**: no new entry point. `ecto_sqlite3` stays dev and test only;
  `ecto_sql` stays optional, and `Explain` is only called when the plugin attached.
  `fixtures/host_app` compiles in prod.
- **Memory bounds**:
  - the explain payload is at most about 16 KB of SQL and 50 small params per event,
    under the existing per plugin caps: the worst case is 500 × ~18 KB ≈ 9 MB per
    session, so the cap on SQL may need to come down to 4 KB (decided in task 3 with
    numbers);
  - N+1 state is bounded per span, with detected groups capped.
- **Security**: EXPLAIN executes against the host's database from the panel. Only seqs
  come from the client, the repo is re-validated, only single SELECT statements run,
  never ANALYZE, always rolled back, with a timeout. Raw params never reach the browser.
- **Host conflicts**: EXPLAIN takes a connection from the host's pool for up to 5 s, one
  at a time per panel (a second click while one runs is ignored).
- **Version compatibility**: adapters differ in EXPLAIN output; we show the raw table.
  `format_table/1` and `query/4` are verified in ecto_sql 3.12. Spans depend on
  LiveView's callback telemetry names on 1.1 and 1.2 (verify in `deps/`).
- **Public API**: `Context.span` and `Event.span` are public (documented, CHANGELOG);
  the `n_plus_one:` option is documented in the README.
- **Tests and ADR sync**: end to end through `DemoWeb.Endpoint` with a real SQLite repo
  for EXPLAIN; FakeRepo stays for the rest.

## Phase 4b: process panel (next plan)

A built-in plugin with a tab for the page's LiveView process. It shows memory, message
queue length, GC info, reductions, links, monitors and `$callers` children. Values come
from `Process.info/2` with an explicit key list, polled through `Panel.send_after/4` only
while the tab is shown and visible (like the component tree), bounded lists. It gets its
own plan after 4a lands.

## Decisions

1. Scope: N+1 (configurable threshold) and EXPLAIN in one batch; the process panel next.
2. Reviews: one combined reviewer per task, two independent reviewers at the end.
3. EXPLAIN params live in the event row, size capped and never rendered (no extra table).
4. EXPLAIN is SELECT only, never ANALYZE, always rolled back.
5. Default threshold 5, `n_plus_one: false` disables the detector.
