# Phase 2 plan: LiveView insights

Goal: on any LiveView page, the panel shows how long each callback took, what changed in
the assigns at every callback, a merged log of server callbacks and client `phx:*`
events, and the live component tree. All of it follows live navigation like the Ecto
and Request tabs (`PhoenixDevToolbar.Page`).

Decisions go into ADR 02, 03, 04 and 06 in place, plus one new ADR 07 (LiveView panel:
pull data, visibility polling, client event bridge) so ADR 04 stays about delivery.
Plugins stay internal (ADR 05 is Phase 3), but everything new is one built-in plugin,
`PhoenixDevToolbar.Plugins.LiveView`, shaped like `Plugins.Ecto`.

## Facts verified in `deps/` (LiveView 1.2.13 and the 1.1.0 hex tarball)

- Span call sites: `mount` and `handle_params` in `utils.ex`, `handle_event` (view and
  component) in `channel.ex`, `render` and `live_component :update` in `diff.ex`.
- `live_component :update` `:stop` metadata is the **start** metadata (parent socket,
  `assigns_sockets` before update): it can be timed, not diffed.
- Component `render` spans run nested inside the LiveView `render` span when the diff
  renders pending components, and also outside it after a `send_update`.
- `Utils.clear_changed/1` sets `__changed__` to `%{}` inside the render span; its values
  can hold **previous** values of nested maps, so we read its keys only, never its values.
- `Phoenix.LiveView.Debug` exists in 1.1.0 with the same API: `socket/1` and
  `live_components/1` are `GenServer.call`s with the default 5 s timeout, return the
  whole socket or every component's full assigns plus `children_cids`.
- Window level client events: `phx:page-loading-start`, `phx:page-loading-stop`
  (`detail: {kind, to}`), `phx:navigate`, and `phx:<name>` for every server
  `push_event` (`LiveSocket.dispatchEvent`). There is no wildcard listener, so the
  loader can only listen to a fixed list.

## Data model

One `:live_view` plugin, events in the session buffer like queries:

| kind | from | data |
|---|---|---|
| `:callback` | `mount`, `handle_params`, `handle_event` (`:stop`, `:exception`); component `handle_event`, `update` | `callback`, `view`, `component`, `cid`, `event` (truncated name), `params` (redacted, truncated, `handle_event` only), `changes` (see below, not for component `update`), `connected?`, `pushed` (`push_event` names, `handle_event` and `handle_params` only), `error` (exception only) |
| `:render` | LiveView `render :stop` | `view`, `force?`, `changed?`, `components`: top 10 component renders folded during this render (`{module, id, count, total_us}`) |

`changes`: at most 20 changed keys (sorted, `:__changed__` and `:flash` keys dropped,
`:flash` shown as a key only); values for the first 10 through `Truncate.redact` and a
smaller inspect (`limit: 20`, `printable_limit: 256`); hard budget about 4 KB per event.
Component renders outside a LiveView render (after `send_update`) are recorded as one
`:render` event with `component` set.

The panel folds, never stores whole lists in assigns:

- `PhoenixDevToolbar.Profile` (like `Summary`): count, total, max per
  `{callback, component, event}` key, at most 100 keys then `other`.
- Event log stream (500 rows): server `:callback` and `:render` events plus client
  events, ordered by arrival.
- Assigns snapshot: one truncated, redacted map of at most 100 keys, replaced on refresh.
- Component tree: at most 500 nodes, replaced on each poll.

## Tasks

Each task is one subagent slice (under ~40 turns), tests first, committed on its own.
Risky tasks (R) get one combined reviewer before the next risky task starts.

1. **`LiveViewCompat.changed_keys/1` and `Truncate.changes/2`** (`live_view_compat.ex`,
   `truncate.ex`)
   - `changed_keys/1`: keys of `socket.assigns.__changed__`, `:all` when it is `nil` or
     missing; never touches values
   - `push_event_names/1`: names from `socket.private.live_temp[:push_events]` (verified in
    1.1.0 and 1.2.13), at most 10, each truncated, payloads never read. Returns
    `{:ok, names}` or `:unavailable` when the field is missing or has another shape;
    `:unavailable` logs one warning per node naming the LiveView version, and the
    callback event gets `pushed: :unavailable` so the panel says why the list is
    empty instead of showing nothing. Tests cover both shapes, the empty case and a
    changed shape (one log line, no raise)
  - `changes/2`: pure builder of the bounded payload above (key cap, value cap, byte
     budget, redaction); doctests plus property style tests on huge and nested assigns
2. **`Plugins.LiveView` callbacks** (`plugins/live_view.ex`, default plugins in
   `application.ex`) (R)
   - Attach to `mount`, `handle_params`, `handle_event` `:stop | :exception` and
     `live_component` `handle_event`, `update` `:stop | :exception`
   - Tests with synthetic `:telemetry.execute/3` in tracked, untracked and `$callers`
     processes, plus a raising payload (quarantine, handler stays attached)
3. **Render events and component fold** (same module) (R, reviewed with task 2)
   - LiveView `render :start` puts an empty fold in the pdict, component `render :stop`
     inside it adds to the fold (capped at 10 entries, smallest dropped), LiveView
     `render :stop | :exception` records and deletes it; component render without a fold
     records directly
   - Tests: fold bounded, pdict clean after `:exception`, untracked path is one pdict read
4. **Harness pages** (`dev.exs`)
   - `/components`: LiveComponents (stateful list, a `phx-target` event, `send_update`
     button), a nested `live_render`, a `push_event`
   - `/assigns`: large list and map assigns, a `password` key, a slow `handle_params`
   - Lets every later task be checked by hand in `PORT=4077 mix dev`
5. **Profile fold** (`profile.ex`)
   - Pure, doctests; key cap; Elixir 1.17 only APIs
6. **LiveView tab: profiler and server event log** (`panel_live.ex`,
   new `panels/live_view.ex` function components, `components.ex`, `panel.css`)
   - One `LiveView` tab with four ARIA sub-tabs (Profiler, Assigns, Events, Components);
     `insert/2` in `PanelLive` routes by plugin to keep the module small
   - Summary bar badge: callback count and slowest callback
   - `LiveViewTest` with seeded Store; the existing end to end test through
     `DemoWeb.Endpoint` grows a click on a real host LiveView and asserts the profiler row
7. **Assigns inspector** (`panel_live.ex`, `panels/live_view.ex`)
   - Per callback diff from `changes` (rows in the Events and Assigns sub-tabs)
   - Snapshot: `start_async/3` calls `Debug.socket(owner)` and truncates **inside the
     task**, so only the bounded map reaches the panel; refreshed when the sub-tab opens,
     on a refresh button, and at most once per second after new callbacks while visible
   - Tests: snapshot of a real host LiveView through `DemoWeb.Endpoint`, redaction,
     dead owner shows a message
8. **Visibility bridge and component tree** (`assets/js/panel.js`, `panel_live.ex`) (R)
   - `panel.js` registers a `PdtPanel` hook on `#pdt-panel` that pushes
     `pdt:visibility` (`open` from the loader's `pdt:state`, `document.visibilityState`)
   - While the Components sub-tab is shown, open and visible: poll every 2 s with
     `start_async/3`: `Debug.live_components/1` for the root LiveView and nested
     LiveViews found through the Store's pid index for the page sids (no
     `Process.list/0` scan); build `{module, id, cid, children}` in the task, drop
     assigns; stop polling otherwise; reset and re-poll on `:navigated`
   - Tests: tree of the `/components` style test LiveView end to end, polling stops when
     hidden, follows navigation
9. **Client event log** (`assets/js/loader.js`, `panel.js`, `panel_live.ex`) (R)
   - Loader adds passive `window` listeners for `phx:page-loading-start`,
     `phx:page-loading-stop`, `phx:navigate`; copies only whitelisted `detail` fields
     (`kind`, `to`, `href`, `patch`, `pop`), strings capped at 256; buffers 50 until the
     frame loads; at most 20 per second, the rest counted; posts `pdt:client` to the
     frame with the existing origin and source checks
   - The whitelist, caps, buffer and rate limiter are pure functions in
     `assets/js/client_events.js`, bundled into the loader, with unit tests under
     `assets/js/test/` run by `node --test` (Node built-ins only, no npm packages).
     `mix test.js` alias, a Node setup step in the CI lint row, part of `mix precommit`
   - `panel.js` forwards to the hook, PanelLive validates (event name in the whitelist,
     sizes) and streams; nothing is stored in ETS
   - Tests: `render_hook` with valid, oversized and unknown events; manual check in Chrome
     DevTools MCP with the console open; `mix assets.build`, commit `priv/static`
10. **Docs, matrix, gate**
    - ADR 02, 03, 04, 06 in place, new ADR 07 and its `adr/README.md` row; CHANGELOG

    - Tests on LiveView 1.1 (`PDT_LIVE_VIEW="~> 1.1.0"`, then restore `mix.lock`),

## Risks

- **Hot path**: the new handlers attach to LiveView events of every LiveView in the
  host. Untracked processes still pay one `Process.get/1` (the `$callers` lookup only
  runs for processes that have callers). Tracked processes pay redaction and bounded
  inspects of at most 10 changed values per callback; render handlers only do pdict
  updates. No `GenServer.call`, no I/O, `rescue` and quarantine as today. Task 3 adds a
  benchmark case to the `bench/` note in ADR 06 or states it is still missing
- **Pdict leaks**: the component fold lives in the LiveView pdict between render start
  and stop; deleted on `:exception` too, capped at 10 entries, so a missed stop costs
  a few hundred bytes until the next render
- **Memory bounds**: callback events are capped at about 4 KB; the 500 events per session
  cap is shared with Ecto (ADR 03 open limit), so a chatty LiveView can push queries
  out: the "+N dropped" badge and the Profile fold (kept in the panel) make it visible.
  Panel assigns are folds, a capped snapshot and capped trees; client events are only
  in a 500 row stream
- **Debug calls**: `Debug.socket/1` copies the whole host socket into our task process
  and blocks the host LiveView for the copy; it runs only on demand, once per second at
  most, while visible. Polling stops when the panel is collapsed, hidden or the tab is
  in the background. The 5 s call timeout blocks a task, never the panel process
- **Host isolation**: the loader only adds passive listeners and never calls
  `window.liveSocket`, never reads `detail` beyond the whitelist (push payloads may be
  large or sensitive), and keeps the existing origin and source checks. The panel's hook
  is ours, registered in our own `LiveSocket`, not the host's
- **LiveView internals**: `__changed__` keys and `live_temp[:push_events]` names are new,
  both read only in `LiveViewCompat`; a changed shape of the latter degrades to
  `pushed: :unavailable` with one warning, never a raise or a quarantine;
  `Debug` and telemetry metadata are public. Verified on 1.1.0 and 1.2.13 sources, run
  on the CI 1.1 row
- **Production footprint**: no new host entry point; the plugin is attached by the
  collector only when enabled; `fixtures/host_app` still compiles in prod
- **Public API and docs**: nothing public changes; new modules are `@moduledoc false`;
  new config keys, if any, documented in `PhoenixDevToolbar` moduledoc
- **Test traps from Phase 1**: the end to end tests drive real host LiveViews through
  `DemoWeb.Endpoint` (not stubbed telemetry) for the profiler, snapshot and tree; JS is
  checked by hand in `mix dev` because `LiveViewTest` does not run it
