# Phase 3 plan: Plugin system

Goal: anyone can add a panel to the toolbar with one module and one config line, and
the built-ins (Request, Ecto, LiveView) are written against that same public API. A
plugin that breaks is disabled and says so in the panel, and one chatty plugin can no
longer push another's events out of the buffer.

Decisions go into ADR 05 in place (it is Accepted, never implemented; the shape below
replaces its draft callbacks), ADR 02 (collector, quarantine), ADR 03 (per plugin caps),
ADR 04 (panel shell) and ADR 07 (LiveView tab on the public API). The Igniter installer
is deferred to its own phase.

## Where we start

- `PhoenixDevToolbar.Plugin` is internal (`@moduledoc false`): `id/0`,
  `telemetry_events/0`, `collect_metrics/3`. No options, no rendering callbacks.
- `Application` hard codes `[Plugins.Request, Plugins.Ecto, Plugins.LiveView]`;
  `config :phoenix_dev_toolbar, plugins:` replaces the list as is, unvalidated.
- `PanelLive` (593 lines) knows every built-in: tabs, streams, `Summary` and `Profile`
  folds, the LiveView snapshot, tree and client events are all its own code.
- Quarantine exists (`Collector`, persistent_term flag, logged once) but is invisible in
  the panel and only released by a new `Collector.attach/1`.
- One cap of 500 events per session for all plugins (ADR 03, trimmed badge since d1e593a).

## Proposed API

```elixir
defmodule MyApp.Toolbar.Jobs do
  use PhoenixDevToolbar.Plugin, id: :jobs, name: "Jobs"

  @impl true
  def init(opts), do: {:ok, %{queues: Keyword.get(opts, :queues, :all)}}

  @impl true
  def telemetry_events(_config), do: [[:oban, :engine, :insert_job, :stop]]

  # Runs in the host process: cheap, pure, never raises (ADR 02).
  @impl true
  def collect(_event, {measurements, metadata}, %Context{config: config}) do
    {:record, Event.new(:jobs, :inserted, %{worker: Truncate.string(metadata.job.worker)},
       duration: measurements.duration)}
  end

  # Runs in the panel process, folded event by event (survives Store trimming).
  @impl true
  def summary_init(_config), do: 0
  @impl true
  def summary_add(count, %Event{kind: :inserted}), do: count + 1
  @impl true
  def badges(count), do: [%{id: "jobs", text: "#{count} jobs", level: :info}]

  # The tab: a LiveComponent rendered in our iframe.
  @impl true
  def panel, do: MyApp.Toolbar.JobsPanel
end
```

- **Collection** (host processes): `init/1` runs once at attach, in the toolbar's
  process; its result is the plugin's `config`, carried in the `:telemetry` handler
  config and handed over in `Context.config` (no lookup on the hot path).
  `telemetry_events/1` takes the config (Ecto needs its repos). `collect/3` returns
  `{:record, Event.t()} | :skip`, as today.
- **Summary** (panel process): `summary_init/1`, `summary_add/2`, `badges/1`. Pure
  folds, unit testable, survive trimming, like `Summary` today, split per plugin.
- **Panel**: `panel/0` returns a module that does `use PhoenixDevToolbar.Panel`
  (a thin `Phoenix.LiveComponent` wrapper). `PanelLive` renders one per enabled
  plugin as a tab and sends it new events (`update/2` with `events`, `page`,
  `visible?`, `reset?`). A LiveComponent gives plugins `handle_event`, streams,
  `start_async` and `send_update_after` (polling) with no API of our own: the
  LiveView tab's snapshot, tree and polling move into its component.
- Optional callbacks: `init/1`, the summary trio, `panel/0` (collection only plugins
  have no tab). `use` sets `@behaviour` and defaults.
- Registration, validated at boot: `plugins: [:defaults, {Mod, opts}, {:exclude, Mod}]`.
  `:defaults` is Request, Ecto, LiveView; a built-in listed with options overrides it.
  An invalid entry, a duplicate id or a module that does not implement the behaviour is
  logged and skipped: the host app always boots.

## Tasks

Each task is one subagent slice (under ~40 turns), tests first, committed on its own.
Risky tasks (R) get one combined reviewer before the next risky task starts.

1. **(R) Behaviour, config and attach.** `Plugin` public with `@moduledoc`, `use` macro,
   `Context.config`, `Config.plugins/0` (expansion, validation, logging), `init/1` at
   attach, config in the handler config. Ecto repos move from app env to plugin opts
   (app env kept as a fallback). Files: `plugin.ex`, `context.ex`, new `config.ex`,
   `application.ex`, `collector.ex`, `plugins/*.ex`. Tests: config expansion matrix,
   a plugin with opts end to end through `Collector`.
2. **(R) Per plugin caps.** Counters `{{sid, plugin}, count, trimmed}` in a new
   `:pdt_counts` table; the writer bumps the plugin's counter and casts a trim for
   that plugin; the Store trims that plugin's oldest events (match on the session's
   range, in the Store process). `max_events` becomes per plugin (500), plus a session
   ceiling (`max_session_events`, 2000) so many plugins stay bounded. Both are tunable
   through the existing `config :phoenix_dev_toolbar, limits: [...]` (ADR 03), now
   documented in the README. Trimmed badge per plugin. Files: `store.ex`, `session.ex`, `panel_live.ex` (gaps). Tests: a LiveView
   flood no longer trims queries; the ceiling holds.
3. **Panel shell.** `use PhoenixDevToolbar.Panel`, tabs and badges built from the
   enabled plugins, events dispatched to each tab's component by plugin id. `Summary`
   splits into the built-ins' `summary_*` callbacks. Request and Ecto tabs become
   components first (simplest). Files: new `panel.ex`, `panel_live.ex`, `components.ex`,
   `panels/*`. Tests: existing panel tests unchanged and green, plus a test plugin with a
   tab rendered end to end through `DemoWeb.Endpoint`.
4. **(R) LiveView tab onto the shell.** Snapshot, tree, polling, visibility and client
   events move from `PanelLive` into the LiveView panel component (`start_async` in a
   component; cancel on page change). `PanelLive` keeps only generic glue (page,
   subscriptions, flush, visibility forwarding). Target: `PanelLive` under 300 lines.
   Tests: `panel_live_view_tab_test.exs` green unchanged, browser check of every sub-tab
   and live navigation (the Phase 2 lock bug lives here).
5. **(R) Quarantine in the panel.** The quarantine stores a truncated banner; the
   plugin's tab shows "disabled after an error" with the banner and a Re-enable button
   (clears the flag). A panel component that raises is caught by a boundary in the shell
   and shown the same way, without killing the other tabs. Tests: raising collector,
   raising `summary_add`, raising render.
6. **Guide and Oban example plugin.** ExDoc guide `guides/writing-a-plugin.md` (hot
   path rules, truncation, attribution limits, testing a plugin). Example
   `examples/oban_panel.ex`: the jobs a page enqueued (`[:oban, :engine, :insert_job,
   :stop]` and friends run in the inserting process; execution runs in Oban's processes
   and is not attributed, said in the guide). `oban` becomes a dev and test only
   dependency, used with the Lite engine on the harness SQLite repo, and a `/jobs` page
   in `mix dev`. Verify event names and metadata in `deps/oban`, not from memory.
7. **Docs.** ADR 05 rewritten in place to the shipped API, ADRs 02, 03, 04, 07 updated,
   CHANGELOG lines, roadmap ticked, `mix precommit`, LiveView 1.1 run, prod fixture,
   then `feature-review` on the Phase 3 range.

## Risks

- **Hot path cost**: the config travels in the `:telemetry` handler config (read with
  the handler anyway), so `collect/3` adds no lookup. The untracked path stays one
  `Process.get`. A third party `collect/3` that is slow is the plugin's cost; the guide
  says so and the collector measures nothing extra.
- **Third party code in host processes**: quarantine covers raise, throw and exit, as
  today. A plugin that blocks (GenServer.call) cannot be stopped from inside the host
  process: documented, not enforced.
- **Production footprint**: plugins are only referenced from config, and the config is
  only read when `enabled?/0`. `fixtures/host_app` gains a configured third party
  plugin and must still compile in prod (the plugin module lives in the host's own dev
  only code path, or the config is under `config/dev.exs`).
- **Memory bounds**: per plugin caps multiply the buffer: the session ceiling keeps
  `plugins × 500` from growing without limit. Plugin ids are atoms from code, never
  from runtime input. Panel components keep streams, never lists.
- **Boot safety**: config validation logs and skips; it never raises in the host's
  application start.
- **Host isolation**: plugin markup renders inside our iframe only. Plugin CSS: plugins
  use our `pdt-` components; no plugin stylesheet loading in this phase.
- **Public API and docs**: everything public gets `@moduledoc`, `@doc`, `@spec`; the
  behaviour is marked unstable before 1.0; built-ins are the reference implementation
  and its test suite.
- **Version compatibility**: verify in `deps/` (1.2 and the 1.1 tarball) that
  `start_async`, streams and `send_update_after` work in LiveComponents on 1.1 before
  task 4. Panel component crash isolation depends on how LiveView reports component
  render errors: verify, don't assume.
- **Regressions**: task 3 and 4 are a refactor of working code: existing tests must stay
  unchanged, and every tab is checked by hand in a browser, including live navigation
  with client events (the Phase 2 lock bug).
- **Tests and ADR sync**: a test plugin under `test/support` exercises the public API end
  to end through `DemoWeb.Endpoint`, not only `LiveViewTest` unit renders.

## Decisions

1. Panel API: a LiveComponent per plugin.
2. Igniter installer: deferred to its own phase.
3. Example plugin: Oban, dev and test only dependency.
4. Caps: 500 per plugin, 2000 per session, tunable via `limits:` in the app env.
