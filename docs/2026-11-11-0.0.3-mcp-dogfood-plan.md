# 0.0.3: MCP dogfood fixes plan

An agent drove the MCP endpoint (ADR 15) through a full Phoenix app (about 25
pages, LiveView events, a live screen with read-only viewer pages). The tools
found a real crash and a real N+1 unaided; these are the problems it hit. Target:
release 0.0.3, stopping at the release commit (no Hex publish).

One change per commit, tests first for T1 to T4, `mix precommit` green before
each commit, ADRs edited in place, one CHANGELOG line each.

## Tasks

### T1: compact `summary/2` and `page_summary` (ADR 13, 15)

`page_summary` is about 25 KB on a normal page: `queries.slowest` and
`callbacks.slowest` carry SQL, params, 10 frames, `times`, assigns changes.

- `Report.summary/2` (`lib/phoenix_dev_toolbar/report.ex`, `summary/2` and
  `slowest/1`) returns compact items by default:
  - slow query: `seq`, `sid`, `origin`, `duration_us`, `rows`, `source`,
    `n_plus_one?`, `error` (nil on success)
  - slow callback: `seq`, `sid`, `view`, `component`, `callback`, `event`,
    `duration_us`, `queries`, `query_us`, `error`
  - error: `seq`, `sid`, `source`, `message`, `origin` (first frame or nil)
  - new types `query_brief`, `callback_brief`, `error_brief` documented;
    `summary` type updated
- `verbose: true` returns today's full items (`query()`, `callback()`, `error()`).
- MCP `page_summary` (`lib/phoenix_dev_toolbar/mcp/tools.ex`) gets a boolean
  `verbose` argument (default false; a non boolean is a tool error).
  `page_queries` and `page_callbacks` are unchanged (the drill-down).
- `page_callbacks` with `sid`: write a test with a dead render plus connected
  mount, call `page_callbacks` with each sid, and assert each returns only its
  own session's callbacks for the LiveView sid, and request plus children for the
  request sid (ADR 13 `children: true`). If they come back identical, fix it.
  Report what the test showed.
- Docs: ADR 13, ADR 15 tool table, `usage-rules.md`, the skill
  (`usage-rules/skills/phoenix-dev-toolbar-report/SKILL.md`, lines 50 to 65).
- Breaking (summary item shape): CHANGELOG line says so.

### T2: LiveView exception stacktraces (ADR 07, ADR 13)

`Plugins.LiveView` keeps only `Truncate.banner/2` on `:exception`
(`lib/phoenix_dev_toolbar/plugins/live_view.ex`, `outcome/4` and `render/3`), and
`Report.error/1` for `:live_view` hardcodes `[]`.

- Store `stacktrace` from the `:exception` metadata in both callback and render
  events, trimmed by a new `Truncate.exception_stacktrace/1`: drop the toolbar's
  and `:telemetry` frames, keep frames up to and including the last app frame
  plus the one frame after it, at most 10 (`@frames`). App frame: a module whose
  application is one of the host's, resolved once at attach time (not in the
  handler) into a `:persistent_term`; when unknown (no Mix), the first 10 frames.
- `Report` reads `data[:stacktrace]` for `:live_view` errors.
- Test (first): a LiveComponent whose `handle_event` raises; assert the error's
  `stacktrace` is non-empty and its first app frame names the raising function.
  Also a render exception.

### T3: unattributed queries and inferred `handle_info` (ADR 13, ADR 02)

LiveView emits no telemetry for `handle_info`, so its queries run in the span
opened after the previous callback's stop (ADR 02 span edges) and no callback
owns them.

- Report only, no hot path change. In LiveView sessions (`kind: :live_view`),
  a query whose `{sid, span}` matches no callback event is unattributed.
  Request sessions are not: their non-callback queries belong to the request.
- `summary/2` gets `unattributed: %{count, total_us, origins}`; `origins` is the
  top 5 by `total_us`: `%{origin, count, total_us}`.
- `callbacks/2` adds inferred entries: `callback: :handle_info`,
  `inferred: true` (real ones `inferred: false`), `view` from the session,
  `queries`, `query_us`, `at` of the first query, `duration_us: nil`. Grouping
  (the documented heuristic): by `{sid, span}`, split where two consecutive
  queries are more than 100 ms apart. `summary.callbacks.count` counts real ones.
- Docs: ADR 13 (heuristic and its limit: several `handle_info` within 100 ms
  merge), skill.

### T4: query origin inside tasks (ADR 08)

In a `Task.async` or `start_async` the user's `fn -> Repo.all(q) end` tail calls
the Repo, so its frame is gone and the origin is
`Task.Supervised.invoke_mfa/2` (or `Phoenix.LiveView.Async.do_async/5`).

- `Plugins.Ecto` `@skip_frames` (`lib/phoenix_dev_toolbar/plugins/ecto.ex`)
  adds `Task.Supervised`, `:proc_lib`, `Phoenix.LiveView.Async`.
- `collect/3` for `source: :caller` stores `initial_call`: the
  `:"$initial_call"` pdict value (one `Process.get/1`), formatted
  `Mod.fun/arity`, nil when its module is skipped too.
- `Report` origin: first stacktrace frame, else `initial_call`, else
  `"task in <View>.<callback> (<event>)"` from the callback owning the query's
  `{sid, span}` (the caller's span, ADR 02). NPlusOne keys stay on the first
  stacktrace frame.
- Tests (first): a query inside `Task.async` from a LiveView `handle_event`, and
  inside `start_async`; assert the origin names app code or the owning callback,
  never `Task.Supervised` or `Phoenix.LiveView.Async`.

### T5: panel socket payload (ADR 04)

The panel's socket pushes 110 to 230 KB per page view. Measure first (bytes
per frame on `/__pdt/socket` in `mix dev` across the harness journey), find what
is sent eagerly (full captures for closed tabs?), push summaries and load detail
when a tab opens, measure again. Numbers go in the commit message and ADR 04.
Runs in a worktree in parallel with T1 to T4 (different files).

### T6: MCP connection docs (ADR 15, guides/agent-setup.md)

Clients connect at startup: starting the dev server after the agent gives
ECONNREFUSED until the client reconnects (Claude Code: `/mcp`). A server bound to
a LAN IP: `.mcp.json` URL with `${PHX_IP:-127.0.0.1}` style expansion.

### T7: release commit

Final review, then `mix bump` (precommit, ci-min, version 0.0.3, CHANGELOG
section, commit and local tag). Not pushed, not published.

## Risks

- **Hot path**: T2 adds a stacktrace trim on `:exception` only (rare) and must
  not call `Mix` in the handler: app modules resolved at attach. T4 adds one
  `Process.get/1` for caller-sourced queries only. T1 and T3 are Report-side
  (caller's process).
- **Production footprint**: none; no new entry point or dependency.
- **Memory bounds**: T2 stacktraces are at most 10 formatted frames per error
  event, already the Ecto and Request limit. T3 inferred entries are derived at
  read time from capped events.
- **Host conflicts**: none for T1 to T4, T6. T5 touches the panel only, inside
  its iframe.
- **Public API**: T1 changes summary item shapes (breaking, CHANGELOG), adds
  `verbose:`; T3 adds keys (`unattributed`, `inferred`), not breaking; ADR 13 and
  15 tables, `usage-rules.md` and the skill stay in sync.
- **Tests and ADRs**: tests first for T1 to T4; ADR 13, 15, 07, 08, 04 edited in
  place.
- **LiveView versions**: T2 relies on `:exception` metadata `:stacktrace`, T4
  on `Phoenix.LiveView.Async` frames: run `agent-tools/ci-min.sh` (LiveView 1.1).
